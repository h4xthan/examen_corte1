Endpoint GET: https://us-east-1.data.tidbcloud.com/api/v1beta/app/dataapp-PZtADZAf/endpoint/book

use dvbs;
-- One row, looked up by id or by isbn, and both parameters are always sent.
--
-- The isbn half is what makes an insert readable. The id is AUTO_RANDOM, does not
-- exist before the statement runs, and a TiDB 8.5 INSERT cannot hand it back:
-- RETURNING is a syntax error on this version. A write endpoint answers with a
-- row count and no rows even when its script ends in a SELECT, so the create
-- inserts and then reads the row back by the ISBN it just wrote, which is
-- UNIQUE.
--
-- A statement that references a parameter which was not sent is refused, so the
-- unused key travels as "" rather than being left out, and NULLIF turns it into
-- NULL, which matches neither column.
SELECT * FROM books
WHERE (id = NULLIF(${id}, '') OR isbn = NULLIF(${isbn}, ''))
LIMIT 1;

Endpoint GET: https://us-east-1.data.tidbcloud.com/api/v1beta/app/dataapp-PZtADZAf/endpoint/books

USE dvbs;
-- ORDER BY and LIMIT are not decoration. Data Service caps an endpoint at its
-- own row limit, and a SELECT with no ORDER BY has no defined order, so an
-- unsorted catalogue is silently truncated to whichever rows the planner
-- produced first. The cap on this endpoint is 1000, measured, not assumed: the
-- reply reports "limit": 1000. Keep the LIMIT here equal to that cap, because
-- whichever of the two is smaller is the number of books that actually come
-- back and the other one is decoration. The shop seeds 200 books and the
-- catalogue page has no paging, so 1000 leaves five times the headroom; past
-- that, rows are dropped without a trace. Raising one side means raising the
-- other, in this file and in the endpoint's settings.
SELECT * FROM books ORDER BY id LIMIT 1000;

Endpoint POST: https://us-east-1.data.tidbcloud.com/api/v1beta/app/dataapp-PZtADZAf/endpoint/books

use dvbs;
-- This endpoint is the UPDATE. Data Service fixes the verb-to-statement mapping
-- at deploy time, which is why the panel's create and edit look inverted here:
-- PUT is the insert and POST is the update.
--
-- NULLIF turns the empty string the caller always sends into the NULL the
-- column holds when there is no cover. A parameter that is referenced but never
-- sent is refused, so the value has to travel even when it is blank.
--
-- id is a string parameter. The key column is AUTO_RANDOM, wider than a float64
-- represents exactly, and sending it as a number would round it on the way out.
--
-- A WHERE that matches nothing is not an error: it reports success having
-- changed no rows. The caller reads the book back afterwards, and that read is
-- what turns "it is gone" into a 404 instead of a 200 for an edit that never
-- happened.
UPDATE books
SET author = ${author},
    title = ${title},
    pages = ${pages},
    isbn = ${isbn},
    price_cents = ${price_cents},
    stock = ${stock},
    url_cover_image = NULLIF(${url_cover_image}, '')
WHERE id = ${id};

Endpoint DELETE: https://us-east-1.data.tidbcloud.com/api/v1beta/app/dataapp-PZtADZAf/endpoint/books

USE dvbs;
-- order_items points at books with ON DELETE RESTRICT and reviews with
-- ON DELETE CASCADE. Deleting a book that still appears in an order fails with
-- 1451, a parent that still has children, and the caller turns that into a 409
-- rather than a 500.
DELETE FROM books WHERE id = ${id};

Endpoint PUT: https://us-east-1.data.tidbcloud.com/api/v1beta/app/dataapp-PZtADZAf/endpoint/books

use dvbs;
-- This endpoint is the INSERT.
--
-- It does not, and cannot, return the row it created, so the trailing SELECT that
-- used to be here was decoration: Data Service answers with the result of the
-- first statement of the script, so a SELECT after an INSERT is executed and its
-- rows discarded. Measured, not assumed: the reply was "1 row affected" with
-- zero rows. RETURNING would solve it in one statement and is a syntax error on
-- TiDB 8.5.
--
-- The caller reads the row back through GET /book with the isbn it sent, which is
-- why isbn is UNIQUE and why that endpoint accepts isbn.
--
-- NULLIF keeps the blank cover out of the column.
INSERT INTO books (author, title, pages, isbn, price_cents, stock, url_cover_image)
VALUES (${author}, ${title}, ${pages}, ${isbn}, ${price_cents}, ${stock}, NULLIF(${url_cover_image}, ''));

Parameter types, for the endpoint declarations:

  id              string   required   always sent. GET /book and DELETE put it in
                                    the query string, POST and PUT in the JSON body
  author          string   required
  title           string   required
  pages           integer  required
  isbn            string   required   always sent. GET /book reads the row back by
                                    it after an insert; "" when looking up by id
  price_cents     integer  required   cents, never a decimal
  stock           integer  required
  url_cover_image string   required   always sent; the NULLIF does the rest
